# Audit Analytics Dashboard

Journal-entry testing on general-ledger data (Buchungsdaten), the way auditors
analyse a client's bookkeeping in a financial-statement audit. Load a CSV export
of journal entries: the dashboard checks the population is complete, runs nine
selection criteria from audit practice (ISA 240) on every posting, gives each
flagged posting risk points, and exports the exceptions and a risk-based sample.

**Live demo of the results:** see `docs/index.html` (published via GitHub Pages).

## Checks

| Check | What it finds | Points | Why an auditor cares |
|---|---|---|---|
| Duplicate postings | same vendor, account, amount, date and text twice | 3 | double payments – error or fraud |
| Segregation of duties | entered and approved by the same user | 3 | four-eyes principle broken |
| Post-closing entries | entered after year end (CPUDT) but dated into the closed year (BUDAT) | 3 | changes the published result after closing (ISA 240) |
| Just below the approval limit | amounts 0–10 % under the limit, counted per user | 2 | invoice splitting to avoid a second approval |
| Entries by rare posters | users with under 1 % of all postings, e.g. a manager | 2 | management override of controls (ISA 240) |
| Entries made late at night | entry time (CPUTM) between 20:00 and 06:00 | 2 | less likely to be reviewed (ISA 240) |
| Weekend & holiday postings | posting dates on Sat/Sun or German public holidays (Baden-Württemberg) | 1 | outside normal working time and controls |
| Round amounts | whole multiples of 1,000 € | 1 | estimates, manual entries, made-up figures |
| Entries without a description | posting text missing or under 4 characters | 1 | no business reason can be checked |
| Gaps in document numbers | missing numbers in the sequence | – | completeness: were postings deleted? |
| Benford's law | first-digit distribution vs. Benford, overall and per user (Nigrini MAD) | – | manipulated amounts break the natural pattern |

**Risk scoring.** Each flagged posting gets the points of every check it fails:
High = 3 or more, Medium = 2, Low = 1. The ranking puts entries that fail several
tests at the top, which is how audit software such as MindBridge or IDEA steers the
sample. The points are a transparent rule of thumb, not a statistical model.

**Population check.** Before testing, the extract is summarised for reconciliation
with the trial balance: number of postings, total, document range, missing numbers,
duplicate keys and months covered (ISA 240 Revised asks for a complete population).

Most checks are SQL queries on an in-memory SQLite table (`audit_checks/checks.py`);
the date and Benford tests use pandas.

## Data

`data/journal_entries_sample.csv` is **synthetic**: 4,007 postings for fiscal year 2025
with SAP-style field names (BELNR, BUDAT, CPUDT, CPUTM, HKONT, DMBTR, LIFNR, USNAM, …),
generated by `data/generate_sample.py` with known, planted anomalies – including a
"management override" scenario: a finance manager who rarely posts books round amounts
after closing, late at night and without a description. Your own CSV needs at least the
columns `BELNR, BUDAT, HKONT, DMBTR, LIFNR, USNAM, FREIGABE`; `BKTXT`, `CPUDT` and
`CPUTM` are optional, and the checks that need them are skipped without them.

## Run it

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/streamlit run app.py          # interactive dashboard
.venv/bin/python -m pytest              # tests: every planted anomaly must be found
.venv/bin/python build_report.py        # rebuild the static page in docs/
```
